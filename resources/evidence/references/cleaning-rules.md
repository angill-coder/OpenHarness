# 清洗规则

改编自 OpenHarness `harness/data_quality_assets/structured_data_prompt.md` 及 `_data_audit.py` 的来源回查规则。保留证据原则，不移植其 Codex CLI、Human Report 质检和打分流程。

## 忠实于材料

- 先清洗、去重、合并和提炼，再输出论据；去掉噪声和重复，不删掉还原使用场景所需的细节。不逐段机械转录整份材料，不写报告或新增结论、建议。
- 覆盖有实质信息的数字、比较、趋势、机制、案例、反例、限制和异常；研究主题只影响顺序，不能删去不支持假设的事实。
- 数值保留对象、时间、样本、单位、分母和比较口径；缺失时说明缺失，不自行补全。百分比、百分点、均值和总量不能混用。
- 时间序列保留阶段变化、峰谷、反转和异常；材料没解释原因就不归因。汇总占比变化不等于同一个体迁移，不能在缺少面板/转移矩阵时写成“用户迁移”。

## 按素材处理

- 访谈：先还原“问题—回答—限定条件”，保留共性、差异、反例和少数意见。采访者的问题、寒暄、口头禅、无答案问题不形成 Evidence；问题中的数字也不能冒充被访者确认的事实。
- 逐字稿与整理稿：同义事实合并，并保留多个真实定位；独立来源数量按原始信源计算，不按文件份数计算。
- 表格：检查相关 Sheet、有效区域与指标族，保留分群、交叉差异、代表案例、异常和口径；不逐行照搬长表，也不能只读第一张 Sheet。
- PDF、Word、图片、Markdown、JSON：按同样原则处理，来源使用真实文件名及页码、段落、标题、表格或单元格；定位不明就如实说明，不猜页码。
- 用户指定的研究纪要/分析材料可以作为来源。分析师归纳无法恢复底层来源时用 `analyst_synthesis`，说明该限制；用户直接更正用 `user_statement` 并保留更正原文的定位。不要把候选报告、范文、Judge 输出或写作要求当作独立事实来源。

## 一条 Evidence 有多大

一条是可独立核验、可独立采用的论据或紧密相关事实组。普通事实通常 1–3 句；用户使用案例按下节保留完整过程，不受这个句数建议限制。不同对象、时间、分群、指标口径或结论方向原则上拆开；同一主题连续问答和重复追问合并。不同事实可能被分别采用或判冲突时不要强行合并。

不设固定条数目标，不为凑条数保留噪声。公司、产品、时间与口径直接写进 `content`；不要另外堆叠公司索引、时间线、置信度评分、解析日志或无关原文。案例内的事件顺序、必要细节和关键原话属于有效论据。

## 用户使用案例：保留到可还原场景

原始素材中，只要某个真实用户或团队围绕具体任务讲述了产品使用经历，就作为案例保留；不要求用户先提出“正文要案例”。保留全部有实质信息的不同案例，包括失败、放弃、负面体验、少数场景和与研究假设相反的经历。纯功能介绍、宣传口号、设想中的用法不冒充真实使用案例；官方展示或分析师转述要明确其性质及核验限制。

- **保存单位**：同一用户/团队围绕同一任务的一段完整使用经历，通常保存为一条 `type=usage_case` 的 Evidence。把相关的连续或跨段问答串回同一场景，保留各段真实定位。不同用户、不同任务或独立使用经历分别保存，不能合成一个不存在的“典型用户”。同一案例内的前后变化、失败重试、跨产品切换与比较保留在一起，不因涉及多个产品或阶段就切碎过程。
- **保存内容**：在 `content` 中按材料实际包含的信息，保留“用户/团队背景—任务及触发原因—使用前做法/约束—产品与使用环境—具体使用过程—结果及用户评价—限制/失败”。过程包括有实质意义的输入、提示词、上传材料、功能/操作顺序、产品输出、人工修改、核验及后续动作。产品名、时间、频率、金额、耗时及比较口径有则保留；关键细节不能被“用于提效”“改善体验”等结论代替。
- **长度与原话**：`content` 仍是字符串，允许多句、多段（JSON 内用 `\n`），不设案例字数、句数或条数上限；长度由还原原始场景所需信息决定，不整篇照搬访谈。可以去掉寒暄、口头禅、重复追问和同义重复；保留影响理解的用户措辞、提示词及关键原话。只有核对过的原文才加引号，转述不伪装成逐字引用；采访者的提问不能变成用户确认的行为或结果。
- **缺失与边界**：只保存材料确实给出的环节，缺失时写“材料未说明”或省略无关环节，不推断身份、动机、操作、因果或效果。影响理解或核验的缺失、过程冲突和无法定位的引文同时写入 `unresolved`；材料只有片段时如实保存为片段案例，不为了叙述完整补情节。不要求为了填写模板给每个缺失环节制造一条问题。
- **去重与来源**：逐字稿、整理稿和重复转引中的同一案例合并，保留最完整的有效细节和多个真实定位；不能仅因同产品、同用途、同结论就合并不同用户。不同材料对同一过程描述冲突时保留各自归属并记录冲突。来自分析师归纳或用户直接补充且未独立核验的案例仍用 `analyst_synthesis` / `user_statement`，在 `content` 标明“使用案例”及来源性质，不升级为已核验访谈。
- **与短论据并存**：案例中的数据或机制确需独立采用时可以另列短 Evidence，但完整案例必须保留；在短论据的 `content` 中注明与哪个案例 ID 来自同一经历，避免重复计为独立用户或信源。原有短论据是同一案例的摘要时，优先在原 ID 下补全；若原论据是跨用户归纳或已独立承担其他事实，则保留并另建案例 ID，不把总体归纳改造成单人经历。

发布前逐个回查素材中的实质案例：每个案例都应能在 JSON 找到对应经历、具体动作、材料给出的结果与限制以及真实来源；不能只检查 JSON 格式或案例条数。Writer 应能据此还原场景而无需猜测。未能读取或保留的部分明确记录，不能报全量完成。

## 缺口与更新

无法读取、无法定位、关键口径缺失和不能消解的冲突写入 `unresolved`。用户指出遗漏或要求补全使用案例时，即使素材指纹未变，也回到 source 重新抽取，不能把旧摘要当作完整案例，不能复制“应该有的结论”作为新论据。更新前检查已有 Evidence，已充分覆盖就不重复新增。仅凭新信息无关、弱相关，不能删除旧有实质论据。
