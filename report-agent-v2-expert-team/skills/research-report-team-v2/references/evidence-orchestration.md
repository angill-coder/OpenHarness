# 主 Agent 如何调用资料整理员

第 0 步默认先委派 `report-team-evidence-v2`，由它整理结构化论据，主 Agent 读取结果后再确认写作输入。清洗说明在该 Agent Prompt 中，配套规则和脚本在 `resources/evidence/`，不再依赖独立 Evidence Skill；主 Agent 不重述完整规则或先自行解析全部素材。

## 何时调用

- 新报告：在第 0 步委派 `operation=prepare`，少量易读素材也调用，完成后再确认写作输入。
- 先在本项目素材目录查找 `structured_data.json`，不要只查当前工作区。已有文件作为 `previousPath` 一并传入，由资料整理员核验格式、来源与 unresolved；与当前资料一致时返回 `EVIDENCE_UNCHANGED` 并复用，不重新清洗或改写共享文件。不能仅凭文件存在跳过核验。
- 用户新增、替换、撤回材料，纠正数据或指出论据遗漏：已有表就 `operation=update`，没有则 `prepare`。单纯“摘要短些、改标题”不调用。事实更新不是 Memory Capture；同轮还包含写作偏好时，报告修订后只把偏好交给 Memory Agent。

## 调用与结果

传入 `caseId`、主题、准确的 `sourcePaths`、完整素材目录 `sourceRoot`、`outputPath` 和 `workDir`：

- `outputPath` 为已确定的 `素材目录/structured_data.json`，保存位置遵循 [统一目录约定](workspace-and-delivery.md)，不追加子目录。
- `workDir` 为该报告内部目录的 `素材处理/r001`，即 `报告目录/.report-agent/<报告标识>/素材处理/r001`，资料更新使用未占用的 r002。它不属于某轮 Loop，单独更新资料或反馈改写也不必创建 Loop。只保存必要解析、扫描记录和用户更正原文，不存论据表快照或旧数据备份。
- 扫描原始素材时排除 `structured_data.json`、`数据版本说明.md`、旧版 `素材清单.json`、`报告/`、指定工作区和解析产物；共享论据只作复用输入，不是新的独立信源。

`caseId` 沿用已有论据表的 `case_id`，首次可用项目文件夹名；同项目后续保持不变。恢复会话时检查已有版本与当前来源，不重复初始化，也不把失败或部分完成的版本冒充完整结果。同一项目的资料更新串行执行，不让两个整理任务覆盖同一输出。

更新另传 `previousPath`（通常等于 `outputPath`）及 `changeRequest`。默认用户不明确指出变化文件，由 Evidence Agent 用素材清单自动比较新增、修改和删除；主 Agent 不先解析整套材料。用户直接提供的数据更正，先把对应用户原文保存为 `workDir/user-update.md`，标明来自用户消息、尚未独立核验，并以绝对路径作为显式来源传入；不得把写作假设或主 Agent 的分析保存成“用户事实”。

收到结果后读取共享文件并核对基本格式、case_id、数量与缺口；按 [素材变化识别](../../../resources/evidence/references/source-changes.md) 调用配套脚本 check 核对 dataVersion/dataSha256，传给后续 Writer。启动 Loop 时登记到新轮需求与运行状态，直接修订时登记到交付版本说明，不改写旧 Loop 的绑定。后续写作和 Loop 直接引用共享文件，不复制数据；相对 `source_ref` 按原始素材根目录解析。版本未登记或指纹不一致时先修复数据登记，不继续使用旧绑定。完整理解论据后再提出 hypothesis，不只读子代理摘要。

- `EVIDENCE_COMPLETED` / `EVIDENCE_UNCHANGED`：使用返回的合法路径。
- `EVIDENCE_PARTIAL`：向用户说明实质缺口；不影响任务可继续，但不能声称全部素材已清洗。影响关键判断时先确认边界或补资料。
- 成员不可用 / `EVIDENCE_FAILED`：如实说明资料整理未完成，不由主理人代替成员、不修改插件或安装配置。不能拿旧版冒充涵盖本次新资料的论据表；保留现有报告，待成员恢复或用户补充必要资料后继续。

## 与写作、Loop 的衔接

初次清洗完成后，主 Agent 继续第 1 步确认，第 2 步按 [Writer 调用与续写](writer-orchestration.md) 委派 Writer 写 R0。输入包传入共享论据表、原始来源路径及 dataVersion/dataSha256；Judge 和 Writer 不各自重新清洗。主 Agent 在每次 Writer 和每批 Judge 调用前后核验绑定指纹；子代理直接回查原始文件时也须确认来源未被替换，已变则返回数据变化，不据新来源评旧版本。

### 资料更新后如何继续

论据更新完成后，主 Agent 根据 `changes`、`summary` 和受影响的报告段落，先在普通回复中简述新增/更正了什么、影响哪些内容、原 hypothesis 是否仍成立；不要回传整份论据表。未读全或存在关键冲突时先说明，不把旧论据冒充更新成功。

用户明确要求“只更新论据”“不要改报告”或仅检查时，报告不动，不调用 Writer 或 Judge。如果论据无变化或变化不影响报告，且没有其他修改或重评要求，说明无需修改后结束。

其余情况，在说明数据变化及影响后，使用 `AskUserQuestion` 确认是否据此修改报告。等待用户同意后，再按 [Writer 反馈分流](writer-orchestration.md#反馈分流) 判断：改变主要结论或需要整体重写时启动新 Loop，局部补充或纠错直接 Rewrite；不同意则保留新数据、报告不动。确认前不派发 Writer/Judge；大改、小改由主 Agent 判断，不交给用户选择。直接改写交付时注明未重新评测，不沿用旧分数。

沿用已确认的受众、场合、篇幅等要求，不重问开场问题。用户同意修改后，由 Writer 据新证据修正观点并说明关键变化；仅在关键事实冲突或必要要求缺失、无法可靠修改时再确认具体问题。

纯写作反馈仍直接按整体影响分流，不增加上述数据更新确认。

重新评测沿用报告目录，在同一报告内部目录下建立新的 `loop-序号-日期时间/`，保存沿用与新增的用户需求、最新数据版本/指纹及原始来源路径，初始化新的 drafting 状态。按 [Writer 调用与续写](writer-orchestration.md) 传入旧报告基线，生成新轮 `候选报告/R0.md`；核验后再执行 Loop。重新冻结标准和评测，新轮首次有效 Judge 后才确定其最佳版本，不继承旧评分、旧采纳结果或停止计数；旧运行和交付报告保持不动。数据版本说明只能追溯，不能恢复未保存的旧数据。

已有 Loop 正在执行时，不热替换其输入表，也不混合新资料与旧评分。收到资料更新先停止后续派发，等待或确认当前 Writer 已停止后再委派新的写作任务，保留当前状态和产物，再整理新资料。需要按新资料运行 Loop 时使用新的 Loop 目录和输入包，重新冻结标准、完整评测；旧 Judgment 不复用。

不为每次数据更新重建历史 Evidence，也不自动清理旧实验的数据副本。论据表默认不作为报告正文或额外交付附件；用户需要时提供当前 `structured_data.json` 及数据版本说明。
