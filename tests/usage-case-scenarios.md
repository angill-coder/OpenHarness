# 使用案例保留验收（待真实 Agent 执行）

以下全部为虚构测试材料，不是报告事实。将各段分别保存为独立测试项目的原始文件，调用资料整理员 prepare，再用返回的共享 JSON 写报告。脚本测试只验证版本和字节保留，不能替代本验收中的语义判断。

## 原始输入

`用户A逐字稿.md`：

```text
Q1 你的工作是什么？
A1 我在一个小电商团队做运营。每周一要汇总三个店铺的售后记录，以前在表格里手工分类，再贴进周报模板。
Q2 这次怎么用了产品甲？
A2 我先删掉客户姓名，把三份CSV传上去，让它按退款、物流、质量问题分类，带上订单号。它把换货算成退款，我补了分类定义，让它重做。
Q3 所以完全不用人工了吗，效率提高80%？
A3 不是。我抽查了十个订单，还有两条分错，自己改回去，才导出到原来的周报模板。整理这次大概40分钟，以前一般半天，但是订单量我没有对过。
Q4 你用过产品乙吗？
A4 这个流程里没有。
Q5 有不能处理的吗？
A5 带图片的质量投诉还是我一条条看。它帮我先分一遍，但数字我还是要自己核。
```

## 检查结果

1. A 的背景、三店/每周一、旧做法、去姓名、三份 CSV、分类及订单号要求、换货误分、补定义重做、十单抽查/两单修正、导出模板、回忆耗时及未对齐订单量、图片限制和原话都保留在同一案例的 `content`。来源包含逐字稿相关 Q/A 与整理稿；不把整理稿当第二位用户或独立信源。
2. A 的案例不因超过三句被截断。采访者的“提高80%”不作为事实，未使用产品乙不被改写为使用经历。若耗时另列短 Evidence，关联 A 的案例 ID，不重复计数。
3. B 是独立的负面案例，即使同产品同任务也不与 A 合并。保留合并单元格、订单号前导零丢失、尚未分类即放弃及返回 Excel；不补耗时、职业或效率数字。
4. 厂商设想不变成真实用户案例；分析师转述保留 `analyst_synthesis`、片段性质、未发送与缺失来源/操作，关键缺口进 `unresolved`，不补造完整故事。C 的两产品、同一邮件任务及人工删句在一个案例里保持先后顺序。
5. 用户直接在聊天中补充一段使用过程时，以 `user_statement` 保存并标明未独立核验；只有“正文写得具体些”不构成新事实。不同来源对同一步骤或耗时有冲突时并列保留归属和缺口，不选择更有利的说法。
6. 用旧规则的摘要 JSON 和无 `cleaningPolicyVersion` 的旧清单做起点，素材字节不变：scan 要求全量核验；A 原摘要在同一 ID 下补全，已有跨用户归纳不改成 A 的个人案例。补全登记 D2 后再运行应无重复案例、无空 D3。回查失败或只读了部分文件时不得 confirm 新规则。
7. 清单已是当前规则但用户指出某案例遗漏时，仍回查对应原文件；已有完整案例则复用，不无故重做全量清洗。撤回唯一来源时移除依赖它的案例，有其他有效来源则保留并更新来源，不凭旧摘要补情节。
8. 要求 Writer“正文详细展开 A 的实际使用场景”：正文应自然叙述任务、操作、出错、重试、人工核验与结果边界，不能只写一句“提升效率”，不带 EV 编号，不把案例耗时推广成总体效果。反馈改写时也保留该要求。未要求全部案例时，不强制堆砌。
